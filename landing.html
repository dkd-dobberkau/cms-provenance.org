The problem

As AI agents weight structured data more heavily, the incentive to manipulate it grows in lockstep.

Schema.org tells a machine what a page is: a product, a person, a price, a review. It cannot tell that machine who made the assertion, when, or whether to trust it.

FAQ and Q&A markup were deprecated as rich results because publishers gamed them. The same dynamic will work through every high-value schema type as the weight placed on structured data grows.

The packaging keeps changing. The pattern stays the same. Decorating a page with rich snippets is not the same as creating a fact-based resource.

CMS Provenance is the layer beneath structured data that closes this gap. A web document carries its own metadata about origin, intent, and authorship, signed by the publisher, addressable down to the individual claim, auditable by anyone.

Four layers · one specification

Adopt one layer.
Or all four.

Each layer is independently useful. Each builds on the one below. Conformance is declared, not imposed. A site reaches whichever level fits its publishing practice today, and moves up as that practice evolves.

01
L2 · Provenance
Authored, sourced, dated

Every document carries a structured record. Author identified by URI, first publication and substantive revision distinguished from technical saves, sources listed with URLs and access dates.

02
L3 · Verifiable
Signed at publish

A canonical hash of the document and its record, signed with the publisher's Ed25519 key. Key rotation supported. Verifiable by any agent without contacting the publisher.

03
L4 · Citable
Facts as first-class

Individual claims within a document become addressable. Subject, predicate, object, source. Exposed as Microdata and as W3C Web Annotations. An agent can cite a sentence, not just a page.

04
L4 · Audit
Well-known endpoint

A site exposes /.well-known/content-provenance with the full index of signed documents, their hashes, signatures, public keys. Paginated, machine-readable, no auth required for good-faith audit.

What it looks like

One JSON-LD block.
Everything signed.

The record sits in the document head, machine-readable, human-inspectable. It points back to the well-known endpoint for verification.

No new file format. No proprietary container. Just JSON-LD that extends schema.org with provenance-specific fields, and an endpoint anyone can query.

// emitted on every signed page

Principles
— 01

CMS-agnostic by design

The specification is owned by no vendor and no platform. TYPO3 ships the first reference implementation. Drupal, WordPress, and Joomla implementations are explicitly planned. Conformance is determined by the spec, not by any one CMS.

— 02

No registry, no gatekeeper

There is no central authority that grants or revokes provenance. Each publisher controls their own keys. Public registries may emerge, but they are never required for conformance. The web stays decentralised.

— 03

Extends, never replaces

Built on schema.org, JSON-LD, W3C Web Annotations, RFC 8288. We do not invent file formats, propose new HTTP verbs, or require new infrastructure. The lift is conceptual, not technical.

— 04

Quality is not in scope

The specification makes provenance legible. It does not rank, score, or evaluate content. Quality remains a judgement made by readers, auditors, search engines, and AI agents. We give them more to work with, not less to think about.

Where we are

A draft, not a manifesto. Yet.

The specification is at draft 0.1. The TYPO3 reference implementation is in product definition. The working group is forming, and the institutional home is being discussed with the Open Website Alliance.

This is the right moment to shape the standard. Editors, agency leads, CMS core contributors, security researchers, and people building AI agents that read the web are all in scope. Especially welcome are voices from outside TYPO3.
