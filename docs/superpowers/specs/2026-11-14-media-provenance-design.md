# Design: Media provenance in the page record (case 1)

Date: 2026-11-14. Status: draft for approval.

## Intent

Today a CPS Record says who wrote a page and on which sources it rests, but nothing about the images and other media on it. The signature covers an image only through its `alt` text (Annex A.2.3); swapping the image file leaves the signature valid, and an agent learns nothing about who made a picture, under which licence it may be used, or whether it was generated by AI.

The user wants media provenance in two steps, modelled on Wikimedia Commons, where every file has its own description (author, source, date, licence) separate from the articles that use it, and the original's bytes are identified by a hash:

1. **Case 1 (this design):** an agent reading a page learns from the page's signed Record where its media come from: creator, licence, copyright, source, and how the media came to exist (camera, AI-assisted, AI-generated).
2. **Case 2 (later, not designed here):** someone who finds a file elsewhere can check, by its hash, whether it really comes from this publisher and is unchanged. That needs a standalone signed record per file at the Audit Endpoint.

Case 1 must not stand in the way of case 2: the data entered for case 1 is exactly what case 2 will publish, and every file gets its stable identifier now.

## Goals

- The Record of a page lists the media used on the page, each with stable identifier, original URL, SHA-256 of the original, creator, licence, copyright notice, source and IPTC digital source type, as far as known.
- The list is part of the Record and therefore covered by the existing Layer 2 signature (Annex A.4 signs the whole Record), without a new signature mechanism.
- Media data is entered once per file in the file metadata, not per use, as on Commons.
- Missing media data never lowers the conformance level of a page. Media appear with whatever data exists.
- The Provenance backend module shows, per page, which media lack creator or licence, so editors can complete them.
- The specification describes the new optional Record members so that other CMS can emit the same shape.

## Non-goals (this version)

- Case 2: standalone media records, a media endpoint under `/.well-known/content-provenance/`, lookup by hash.
- C2PA: no manifests are read, emitted or referenced.
- Hashes of processed variants (scaled, cropped, converted files). Only the original is hashed.
- MX carriers for media (XMP in the file, `.mx.yaml` sidecars). The same metadata can feed them later.
- Online media helpers (YouTube, Vimeo files in FAL); they have no original bytes on the site.
- Media outside content elements: `pages.media`, images from TypoScript, CSS backgrounds, external URLs in RTE content.
- Editing media data in the Provenance module; editing stays in the file metadata form.

## Anti-goals

- A page must never lose L2/L3 because a file lacks a creator or licence. Existing sites with many legacy images must keep their level.
- The frontend must not write to the database while rendering (no lazy hash or identifier assignment on page view).
- The Record must not claim more than is known: no empty strings, no guessed licences, no default digital source type.
- No change to Annex A canonicalisation of the page text; existing signatures and test vectors stay valid.

## Constraints

- TYPO3 13.4 and 14, PHP 8.2+, like the other extensions.
- Record emission is cached page output (`JsonLdHeaderData`); media data must be available at render time from the database without file I/O.
- Signing (`provenance_signing`, listener `SignPageContent`) signs the Record found in the final HTML; anything the core builder puts into the Record is signed automatically. No change to the signing extension is expected, apart from the check under "Keeping Records current".
- Records may contain integers only (Annex A.4); file sizes or dimensions, if ever added, must be integers.
- Code, labels and docs in English with XLIFF labels.

## Approaches

| | Approach | Trade-off |
| --- | --- | --- |
| **A (chosen)** | Media list inside the page Record, signed with the page; every file has a stable `urn:uuid` | Reuses signature and Audit Endpoint. Verifying a medium requires loading the page, which is what case 1 is for. Case 2 can turn the same identifier into a standalone record without migration |
| B | Standalone signed media records now, the page only references them | Solves case 2 at once, but needs a second signing input, a new endpoint, variant resolution and new conformance rules; roughly three times the work for a case the user explicitly postponed |
| C | Unsigned schema.org `ImageObject` in ordinary JSON-LD | Cheapest and already read by search engines, but nothing is signed, which contradicts the core of CPS |

The user chose A. Emitting additional plain schema.org data (C) alongside is not needed, because the Record already is schema.org JSON-LD.

## Decisions

### Record shape

The Record gains three optional members, using schema.org properties of `CreativeWork`:

| Member | Content |
| --- | --- |
| `image` | Array of `ImageObject` |
| `video` | Array of `VideoObject` |
| `audio` | Array of `AudioObject` |

The type is chosen from the file's MIME type (`image/*`, `video/*`, `audio/*`); other file types (PDF, documents) are not listed in this version. Each entry has, leaving out what is unknown:

| Property | Source in TYPO3 | Note |
| --- | --- | --- |
| `@id` | `sys_file.tx_provenance_media_uri` | Stable `urn:uuid`, one per file, never reused |
| `contentUrl` | Absolute public URL of the original file | Omitted for storages without public URL |
| `sha256` | `sys_file.tx_provenance_sha256` | Lowercase hex over the original file's bytes |
| `encodingFormat` | `sys_file.mime_type` | |
| `creator` | `sys_file_metadata.creator` | Object `{"name": …}` without `@type`, because the free-text field often names an agency rather than a person (author's call); no URI required, unlike Record authors |
| `copyrightNotice` | `sys_file_metadata.copyright` | |
| `license` | `sys_file_metadata.tx_provenance_license` (new) | Absolute URL, for example a Creative Commons licence URL |
| `isBasedOn` | `sys_file_metadata.source` | Only if the value is an absolute URL; otherwise omitted |
| `digitalSourceType` | `sys_file_metadata.tx_provenance_digital_source_type` (new) | IPTC Digital Source Type IRI |

Entries are ordered by first appearance on the page and each file appears once, even if used several times. Translated metadata is taken in the page's language; `license` and `digitalSourceType` are not translatable (`l10n_mode: exclude`).

`alt` text stays where it is: in the canonical page text (Annex A.2.3). It is not repeated in the media entries.

### Which media are listed

The file references (`sys_file_reference`) of the content elements rendered on the page: visible `tt_content` records of the page in the current language, respecting enable fields and workspaces as the frontend does. Online media helpers are skipped. This is decided from the database, not by parsing the HTML, so it can be computed in the cached header data.

### Data entry

- The core extension requires the system extension `filemetadata` (`typo3/cms-filemetadata`), which provides `creator`, `copyright` and `source`. Without it the core has no creator field.
- Two new fields on `sys_file_metadata`: `tx_provenance_license` (link field, URL only) and `tx_provenance_digital_source_type` (select, empty by default). Select values are IPTC Digital Source Type terms; at least `digitalCapture`, `compositeWithTrainedAlgorithmicMedia` and `trainedAlgorithmicMedia` (the three MX maps to), the full list to be taken from `https://cv.iptc.org/newscodes/digitalsourcetype/` by the builder.
- Two new columns on `sys_file` (not on metadata, because they belong to the bytes, not to a language): `tx_provenance_media_uri` and `tx_provenance_sha256`, plus `tx_provenance_sha256_of` holding the `sys_file.sha1` the SHA-256 was computed for, so a replaced file is detected.

### Filling identifier and hash

- On indexing and on file replacement or content change (FAL events after a file is added to or updated in the index), the core assigns the identifier if missing and recomputes the SHA-256 when `sys_file.sha1` differs from `tx_provenance_sha256_of`.
- The existing `provenance:backfill` command gains an option (or a sibling command) that fills both for files already in the index.
- At render time a file without identifier or with a stale hash is still listed, without `@id` or without `sha256` respectively. The backend module reports it.
- A replaced file keeps its identifier; only the hash changes, as file versions on Commons do.

### Hash history (decided by the user)

Every SHA-256 a file has had is kept in a new table, for example `tx_provenance_media_hash` with `media_uri`, `sha256`, `valid_from` and `valid_until` (null for the current version). A row is written whenever a hash is computed or recomputed; the previous row is closed. Case 1 does not publish the history; it exists so that case 2 can later check copies of earlier versions that were signed into earlier page Records. Without it that data would be lost for good. Rows are never deleted when a file is replaced; deleting a file closes its current row.

### Keeping Records current (decided by the user)

A Record must never carry a hash or media data that no longer matches the file. Therefore:

- While rendering the header data, the page is tagged with one cache tag per listed file (for example `sys_file_<uid>`).
- Saving a file's metadata (`sys_file_metadata`, also in other languages) and replacing or updating a file in the index flush exactly these tags, after the identifier and hash have been updated.
- The flushed pages are regenerated on the next request and signed anew by `SignPageContent`. The builder verifies that re-signing also updates the row the Audit Endpoint serves (`tx_provenancesigning_record`); if it does not, the signing extension needs that change, which would then be the only change there.

### Backend hint

The Pages submodule of the Provenance module shows a media column per page: the number of media on the page and how many lack creator or licence. The detail lists the affected files with a link to their metadata form. Files without identifier or current hash are reported too, with the hint to run the backfill command. Media data never appears in the "missing for next level" list, because it does not affect the level.

### Specification changes

In `content-provenance-spec`, listed under "Changes since Draft 0.4":

- Section 3.1: the optional members `image`, `video`, `audio` with the entry shape above. Media members are not part of completeness; a Record is complete without them and with incomplete entries.
- `sha256` is computed over the original file as published at `contentUrl` at the time of signing. Verifiers MUST NOT expect a differently sized or converted variant served in the page to match it. Publishers MUST re-issue the Record when a listed file is replaced, so the signed hash matches the file at `contentUrl`.
- A note that the Layer 2 signature covers the media list as part of the Record, which binds the page to the original files' hashes, and that standalone media records are left to a later draft (case 2).
- Section 5: the C2PA row and the MX crosswalk mention media; MX Carrier Formats §3.5/§3.7 (XMP, `.mx.yaml`) and MX's derivation of IPTC `digitalSourceType` are named as compatible, not adopted.
- Vocabulary: if `sha256` or `digitalSourceType` are not (or only as pending) defined in schema.org, they are defined in `vocabulary/v1/context.jsonld` and mirrored in `ns/v1/context.jsonld` of this site.

The conformance repository gets one canonicalisation vector with a Record that contains a media list, to show that it is signed like any other member.

## Left to the builder

- Exact FAL events to hook for identifier and hash on TYPO3 13.4 and 14.
- Query shape for the page's file references (one query per page, not per content element) and how translations and workspace overlays are applied.
- Full IPTC value list and labels.
- Whether the backfill is an option of `provenance:backfill` or a separate command.
- Layout of the media column in the Pages submodule, following the existing module design (`2026-11-14-provenance-backend-module-design.md`).
- Verifying in the current schema.org release whether `sha256` and `digitalSourceType` are stable or pending, and deciding the vocabulary change accordingly.

## Later

- Case 2: standalone signed media records at `/.well-known/content-provenance/media/{id}`, lookup by SHA-256, resolution of processed variants to their original.
- MX: emitting XMP or `.mx.yaml` from the same metadata; feedback to Tom Cranstoun on the conflicting MX XMP namespaces.
- C2PA: reading existing manifests from uploaded files and referencing them from the media entry.
